- **Tier 1 #1: FSR2 upscaling re-enablement — the atomics/uniformity Tint bug was never actually an ICE; found, fixed, and verified, but FSR2 stays disabled on WebGPU for a new, precisely-scoped reason.** The believed blocker (a Tint "internal compiler error", size/complexity-triggered, estimated 3-7 days, possibly needing upstream Tint work) turned out, on direct reproduction via `tint_convert_cli`, to be a genuine WGSL uniformity-analysis validation error instead: `workgroupBarrier` must only be called from uniform control flow. Root cause: Tint's WGSL writer recognizes the idiom `barrier(); read a shared var; barrier();` as safe and rewrites it into the `workgroupUniformLoad` builtin the analysis trusts — but only when those three things are literal, adjacent instructions in one function; FSR2's `SpdExitWorkgroup` (`thirdparty/amd-fsr2/shaders/ffx_spd.h`) read its last-active-workgroup counter through two trivial wrapper-function calls that hid the shape from Tint's pattern-matcher, and only had one barrier to begin with. Fixed in two parts: (1) `SpdExitWorkgroup` now reads the shared counter directly instead of through the wrappers, with a second (harmless) barrier added to complete the shape; (2) added an 18th SPIR-V preprocessing pass, `eliminate_local_single_block_vars` (`drivers/webgpu/spirv_preprocess.h`/`.cpp`, SPIRV-Tools' `CreateLocalSingleBlockLoadStoreElimPass` + `CreateAggressiveDCEPass`), since glslang's unoptimized codegen still round-tripped the read through a local variable that broke the same adjacency. Verified: generated WGSL now literally contains `workgroupUniformLoad(&(spdCounter))`; a full 344-shader corpus A/B test (building `tint_convert_cli` with/without the new pass) confirms zero regressions. Found and fixed two more bugs along the way (both previously unreachable since FSR2 was never instantiated on WebGPU before): FSR2's two SNORM16 lookup textures used a texture format this driver correctly refuses to support (fixed by converting to R16_Sfloat with proper SNORM→float value conversion via `Math::make_half_float()`), and `ShaderRD` compiling every declared shader-mode variant regardless of dispatch selection meant WebGPU was also compiling FSR2's image-atomics shader variant, which is unconditionally fatal there for an unrelated, harder reason (`OpImageTexelPointer` has no WGSL translation at all) — fixed by only declaring that mode when the backend actually supports image atomics. **Remaining blocker, found via live browser verification**: FSR2's RCAS/accumulate-sharpen passes write through a deliberately formatless storage image (AMD's own comment: "app controlled format") with no WGSL equivalent — the same class of gap as this project's own Task 8.3 (previously known to affect only `screen_space_reflection_filter.glsl`), now confirmed as its own separate instance. The FSR2 SDK also doesn't handle this specific failure gracefully (crashes the whole engine rather than just failing the upscale), so FSR2 stays gated off on WebGPU behind a new, correctly-scoped `RD::SUPPORTS_FORMATLESS_STORAGE_IMAGES` capability flag (mirroring `SUPPORTS_IMAGE_ATOMIC_32_BIT`'s precedent) rather than the old atomics-based gate — identical, safe fallback-to-no-upscaling behavior as before this session, but the real remaining blocker is now Task 8.3, not a vague Tint-ICE placeholder. Files: `thirdparty/amd-fsr2/shaders/ffx_spd.h`, `drivers/webgpu/spirv_preprocess.{h,cpp}`, `drivers/webgpu/rendering_device_driver_webgpu.cpp`, `drivers/webgpu/tint_cli/main.cpp`, `servers/rendering/renderer_rd/effects/fsr2.cpp`, `servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp`, `servers/rendering/rendering_device_commons.h`, and the Vulkan/Metal/D3D12 driver `has_feature()` implementations. See `webgpu_notes/TASKS.md` Task 9.10 for the full investigation.
- **Skeleton atlas defragmentation — fixed.** The atlas only had a bump allocator; freeing (`skeleton_free`) or resizing (`skeleton_allocate_data` with a different bone count) a skeleton never reclaimed its slot, so a long-running scene with skeleton churn (spawned/destroyed enemies) grew the atlas without bound even at constant live count. Added a free-list allocator layered on the bump allocator: frees/resizes return their slot to a sorted, coalesced free list; freeing the exact tail shrinks the high-water mark directly (cascading through trailing free blocks) instead of growing the list; new allocations first-fit against the free list before bump-allocating; once free space exceeds ~25% of the used region (min. 16K-float floor), an automatic compaction pass repacks all live skeletons contiguously via `RID_Owner::get_owned_list()` and re-uploads in one `buffer_update_direct` call. Also fixed a related latent bug found in the process: growing the atlas GPU buffer's capacity discarded the old buffer's contents for any live-but-not-currently-dirty skeleton (only the dirty region got re-uploaded to the new buffer) — now the full used region is re-uploaded immediately after the new buffer is created. Files: `servers/rendering/renderer_rd/storage_rd/mesh_storage.h`/`.cpp` (shared RD code, all backends). Verified with a standalone `std::vector`-based reimplementation of the algorithm covering tail-shrink, middle-slot reuse, coalescing (both insertion orders), automatic defrag → gap-free contiguous packing, byte-level data preservation across the defrag `memmove`, and 2000 iterations of randomized alloc/free churn checking free-list invariants and no live-slot overlap after every operation; native `linuxbsd` editor build compiles clean. See `webgpu_notes/perf_optimization_may3_2026.md`'s "Follow-up fix" note for full detail.
