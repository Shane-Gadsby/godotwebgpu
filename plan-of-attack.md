### Phase 1: SDFGI brightness runaway — the single active blocker for a public build

**What it is**: with SDFGI enabled, WebGPU's rendered brightness/exposure climbs continuously over time until the scene goes solid white; native Vulkan stays pixel-stable indefinitely with identical shader code and settings. This is the *only* thing currently blocking a public build (everything else in this fork works).

**Where 39 rounds of investigation (Task 9.5, item 11 in `webgpu_notes/TASKS.md`) have landed**, in the order each was ruled out or confirmed:

- **Ruled out**: a storage-image-format bug (Round 30's clamp-relocation test), quantization/damping loss (Round 31's bit-exact-flat-on-Vulkan numeric capture), the cascade-array-binding-collapse bug (Round 36 found and fixed a *real*, independent bug here — cascade arrays were silently collapsing to element 0 via `flatten_binding_arrays` — but Round 37 proved fixing it does not stop the runaway), the self-illumination bounce-feedback loop (Round 34: runaway still happens, just slower, with feedback fully disabled), and push-constant delivery of `history_index` (Round 35: cycles in perfect lockstep with the true CPU value).
- **Confirmed**: the divergence traces to `lightprobe_average_tex` (`sdfgi_integrate.glsl` ~L330-346's hand-rolled, non-atomic rolling-average accumulation: `average -= prev_value; average += ivalue;`) — a plain 2D texture with no storage-format branching at all, read and written at the *same texel on every consecutive frame* (zero slack between one frame's store and the next frame's load). Round 38: forcibly clearing this texture every frame (breaking its intended persistence) makes the runaway disappear entirely; clearing the *other* persistent SDFGI texture (`lightprobe_history_tex`, which has ~30 frames of slack per texel via its ring-buffer layout) does not affect the runaway either way.
- **Round 39's key result**: artificially adding scheduling slack between the write and the next read (skipping the accumulation dispatch on a schedule, simulating what a 2-layer ping-pong buffer would provide) *reduces* the growth rate substantially (≈27,472/dispatch at zero slack → ≈1,506/dispatch at a 2-frame gap → ≈636/dispatch at a 4-frame gap) but does **not** trend to zero, and the per-doubling improvement is shrinking (18x, then 2.4x) rather than showing a hard cutoff.

**Working theory**: this shape — same-texel same-texture compute-to-compute read-modify-write across separate `wgpuQueueSubmit()` calls, more slack helps but doesn't fully fix it — looks like a **probabilistic race in WebGPU/Dawn's automatic hazard tracking** (this driver's `command_pipeline_barrier` is a documented no-op; WebGPU has no manual barrier API at all — hazard tracking is automatic and mandatory by design, not an opt-out), not a fixed-latency visibility delay a bigger buffer could deterministically absorb.

**Investigation plan**:

1. **Build a minimal, from-scratch WebGPU reproduction outside Godot entirely** (a single HTML/JS file or small native Dawn C++ program — not a Godot scene). Reproduce only the essential pattern: one compute shader, one persistent storage texture, one texel read-modify-written every frame (`avg -= old; avg += new; store`), across N separate `queue.submit()` calls with no explicit synchronization beyond WebGPU's own automatic tracking. Run it under the same Chrome/Vulkan/Linux configuration this project already uses for real-GPU testing (`webgpu_tests/scene_smoketest`'s `--enable-unsafe-webgpu --use-vulkan --use-angle=vulkan` flags are the known-working baseline flag set).
   - **If it reproduces**: this is very likely a genuine Dawn/Chromium bug, isolated with a minimal, reportable test case. Proceed to step 2.
   - **If it does not reproduce**: the bug is Godot-specific, not a Dawn hazard-tracking gap — see step 4 instead.
   - **DONE, 2026-09-14 (Task 9.5 Round 40)**: built `webgpu_tests/sdfgi_race_repro/`, the exact telescoping-accumulator pattern from `sdfgi_integrate.glsl`, run at real-GPU scale (RTX 4080 SUPER, same Vulkan/Chrome flags) — 1,000 and 8,000 accumulate calls per slack value across slack 0-128 (~72,000 total touches in the larger run). **Did not reproduce at any slack value, including zero slack.** This is a real negative result against the "probabilistic Dawn hazard-tracking race" theory (WebGPU's spec guarantees same-queue submission-order execution with automatic hazard tracking for exactly this pattern — a race here would be a fundamental Dawn conformance bug, and none was found after tens of thousands of touches).
   - **DONE, 2026-09-15 (Task 9.5 Round 41)**: rebuilt the exact same repro through the *real* submission path the driver actually uses — `wgpuQueueSubmit()`/`webgpu.h` via Emscripten's `emdawnwebgpu` port (`native_emdawnwebgpu_repro.cpp`), not raw browser JS — since a pure-JS repro can't see a bug in the C-API-to-JS glue layer itself. Same result: **zero divergence** at 8,000 calls × slack 0-16 and 1,000 calls × slack 32-128. **Routing to step 4's "not reproducible" branch** — see below.
2. **With the minimal repro in hand, binary-search for what actually eliminates the race**, since Round 39 already showed added slack alone doesn't fully do it:
   - Try forcing a full GPU idle between frames (`wgpuQueueOnSubmittedWorkDone()`/`wgpuDeviceTick()`-equivalent, awaited before the next frame's dispatch) — if this *fully* eliminates the divergence (not just reduces it), that's decisive confirmation of a cross-submission hazard-tracking gap, at the cost of a real, measurable per-frame stall.
   - Try issuing the read-modify-write from a single command buffer per "logical frame pair" (encode both this frame's read of last frame's result and this frame's write in one submission, if the surrounding architecture allows it) to see if intra-submission ordering (which Dawn is far more likely to track correctly) sidesteps the issue entirely.
   - Try the same repro on a second Dawn backend if available in this environment (e.g. D3D12 or the software/SwiftShader Vulkan path) to check whether this is Dawn's Vulkan backend specifically, or something more fundamental to Dawn's hazard tracker generally.
3. **Route the outcome**:
   - **Confirmed Dawn/Chromium bug**: file it upstream (chromium.org's Dawn issue tracker) with the minimal repro. In parallel, decide on a scoped Godot-side workaround — the most practical is still probably ping-pong/double-buffering `lightprobe_average_tex` (2 layers, alternate by frame parity, mirroring `lightprobe_history_tex`'s own already-safe ring-buffer design) even though Round 39 showed it doesn't reach zero — combined with whichever explicit-wait mechanism step 2 found actually works, applied narrowly to just this one texture's access pattern rather than as a global stall.
   - **Not reproducible standalone**: re-examine Godot-specific state that step 1's minimal repro wouldn't have — in particular, whether `FramebufferCacheRD`/`UniformSetCacheRD`'s caching layers could be handing back a *stale* texture view across frames (a cache key collision or missed invalidation would look exactly like "safe on Vulkan, corrupted on WebGPU" if WebGPU's view/binding model is more sensitive to it), and whether Emscripten's single-threaded WASM event-loop timing (queue submission relative to `requestAnimationFrame`/JS microtask ordering) introduces a distinct race Dawn's native hazard tracker wouldn't otherwise have to handle. Instrument `lightprobe_average_tex`'s actual bound `WGTexture`/view pointer (not just its logical RID) across consecutive frames in the real Godot repro to rule this in or out directly.
     - **DONE, 2026-09-15 (Task 9.5 Round 41), cache theory**: read (not tested — didn't need to be) `gi.cpp`'s `SDFGI::create()` and the WebGPU driver's `uniform_set_create()`. `cascades[i].integrate_uniform_set` is built by a direct, non-cached `uniform_set_create()` call once per cascade creation and reused via a fixed `RID` every frame; the driver builds one `WGPUBindGroup` at that same creation time, and WebGPU bind groups pin their resource views for their own lifetime. **No per-frame cache lookup happens in this path at all, so "stale cached view" is structurally ruled out for this specific accumulator.** (Doesn't rule out `FramebufferCacheRD`/`UniformSetCacheRD` staleness as a bug elsewhere — only that it can't be behind *this* symptom.)
     - **Still open**: the Emscripten event-loop-timing angle, and the actual live-instrumentation step (log `lightprobe_average_tex`'s bound texture/view pointer + frame counter in the real Godot repro against the user's scratch project) — this is now the most promising concrete next action, since both leading theories (Dawn race; cache staleness) have been checked and found wanting.
4. **Throughout**: keep using the methodology this task has already established — real GPU (not software/sandboxed) testing via `webgpu_tests/scene_smoketest`'s real-GPU Playwright flags where possible, `md5sum`-verify the exported `.wasm` against the freshly built `bin/` output before trusting any "fixed"/"still broken" result (Round 23's stale-export-template trap cost real time before being caught), and a 60-second-plus capture window before trusting any "zero errors" result (Round 20's async-error-timing correction).

### Phase 2: Eliminate the runtime Tint-conversion fallback for specialization-constant variants

**What the plan previously called this**: "Pre-compile WGSL at export time (full coverage) — extend `wgsl_precompile.py` to cover every reachable shader variant ahead of time." Investigation this session found that framing is likely the wrong shape of fix for the dominant remaining category — brute-force enumerating every specialization-constant *value combination* ahead of time doesn't scale (values can be scene/asset-dependent, e.g. light or decal counts) and doesn't need to, because the driver already has unused machinery built for a cleaner fix. Both angles are laid out below; investigation should confirm which is actually needed before writing code.

**What's already known** (from Task 9.5's Round 20-23 SDFGI investigation and direct code reading this session):

- Godot's specialization constants (`RenderingDeviceCommons::PipelineSpecializationConstant`) are always simple scalars — `BOOL`, `INT`, or `FLOAT` (`servers/rendering/rendering_device_commons.h` ~L680-682). There is no array-size or structural specialization type in the API surface the driver has to support — every specialization constant is, by construction, exactly what WGSL's `override` mechanism is designed to substitute at pipeline-creation time.
- The driver already has a complete, working implementation of exactly that: `command_bind_render_pipeline()`-adjacent pipeline-creation code (`rendering_device_driver_webgpu.cpp` ~L9238-9270, mirrored for compute ~L9945-9989) builds `WGPUConstantEntry` arrays from `p_specialization_constants` and passes them to Dawn's native pipeline-constants API — its own comment states the intent directly: *"pipeline constants instead of creating specialized shader modules. This eliminates all runtime SPIR-V patching and Tint conversion."* This path (`use_override_path`) reuses one precompiled base WGSL module and substitutes values at pipeline-creation time, with **zero runtime Tint conversion needed regardless of how many distinct value combinations exist**.
- `use_override_path` is gated on `shader->has_override_declarations`, set by scanning the base module's own Tint-generated WGSL for `@id(N) override` declarations. **This is always false in practice**: `freeze_spec_constant_ops` — the very first of the ~18 SPIR-V preprocessing passes, run unconditionally on every shader's base module — evaluates every `OpSpecConstantOp`/`OpSpecConstant*` to its literal default value and strips the `SpecId` decoration *before Tint's SPIR-V reader ever sees the bytes*. There is nothing left for Tint to represent as a WGSL `override` by the time it runs.
- Because of this, **every pipeline that ever needs a non-default specialization value unconditionally takes the "legacy path" instead**: `_create_module_with_spec_constants()` re-patches the shader's *original, pre-preprocessing* SPIR-V with the real values baked in as literal constants, then reruns the *entire* preprocessing pipeline and a fresh Tint conversion, at runtime, once per distinct (shader, value-combination) the engine ever actually requests. This is the actual "runtime Tint fallback" the original plan item wanted to close.
- This legacy path is not just a performance/coverage gap — it has at least one documented, still-open **correctness bug**: it doesn't correctly duplicate every WGSL-text-level fixup the primary module gets (the RW-storage-texture split in particular — `webgpu_notes/TASKS.md`'s Round 20-23 SDFGI trail, "Item 3, root-caused but not landed," reverted and left open specifically because the bind-group/BindGroupLayout plumbing for a split discovered only during specialization was never built).

**Investigation plan**:

1. **Confirm why `freeze_spec_constant_ops` evaluates everything unconditionally**, before assuming it's safe to change. Check its git history/original commit message and any referenced task in `webgpu_notes/TASKS.md` for the reason it was written this way — it may be an intentional, general simplification rather than a hard requirement. Specifically check whether Tint's SPIR-V reader has any known gaps handling `OpSpecConstantOp` (computed expressions over spec constants, as opposed to a bare `OpSpecConstant`) — if some *forms* of Godot's spec-constant usage genuinely can't survive to become a WGSL `override` (e.g. a spec constant that feeds an `OpSpecConstantOp` used to compute an array bound or similar SPIR-V-level constant expression, even though the RenderingDevice-level API only exposes scalar types), the fix will need to distinguish "this constant ID is safe to leave overridable" from "this constant ID's *use* requires compile-time resolution" rather than a blanket toggle.
2. **Prototype the minimal version**: make `freeze_spec_constant_ops` conditionally skip evaluating a spec constant when it is *only* ever consumed as a plain runtime value (i.e., its `OpSpecConstant` result feeds directly into ordinary instructions Tint's WGSL writer already knows how to lower to a real WGSL `override`-backed expression, not into another `OpSpecConstantOp`/type-defining instruction it would need to fold at compile time). Confirm this is even expressible as a scoped change to one pass rather than needing new plumbing elsewhere (in particular: does Tint's SPIR-V reader correctly turn a surviving `OpSpecConstant` + `SpecId` decoration into a WGSL `@id(N) override` on its own, or does it need help — check by hand-constructing a tiny SPIR-V module with a genuine unfrozen spec constant and running it through `tint_convert_cli` directly).
3. **Verify the existing WGPUConstantEntry/`use_override_path` plumbing actually works once fed real overridable WGSL** — it's unclear this path has ever been genuinely exercised (there's no evidence anything in the current shader corpus has ever produced `has_override_declarations == true`). Write a small standalone test shader with a real spec constant surviving step 2's change, precompile it once, and confirm the pipeline-creation code correctly passes its value via `WGPUConstantEntry` and produces correct output at two different specialization values without any second Tint conversion. This is the step most likely to surface that the "already-built" plumbing has its own latent bugs (untested for years is not the same as working).
4. **Re-run the full regression suite plus a targeted spec-constant-heavy scene** (SDFGI is the known heaviest user of the legacy path per the Round 20-23 trail) after the change, and specifically re-attempt Round 20's abandoned fix — the RW-storage-texture split correctness bug in `_create_module_with_spec_constants()` — to see if it's now moot (no longer reachable, because the shader in question no longer needs the legacy path at all) rather than something that still needs its own separate fix.
5. **For whatever legacy-path usage remains** (any spec constant step 1/2 determine genuinely can't be made overridable): only *then* fall back to the original framing — extend `wgsl_precompile.py`'s ahead-of-time coverage for those specific cases. Given step 1's constraint (values may be scene-dependent), this likely means identifying a bounded, enumerable subset (e.g. boolean feature toggles with only 2 states) rather than attempting full combinatorial coverage, and documenting explicitly which specialization patterns are structurally excluded from ahead-of-time coverage and why.
6. **Verification for the whole phase**: `shader_corpus` and `preprocessing_tests` must stay green throughout (they don't exercise specialization constants directly today — check whether they need a new fixture added to actually cover this path, since its near-total lack of dedicated test coverage is part of why `has_override_declarations`'s permanent falseness went unnoticed this long); `driver_unit_tests` 327/327; native editor + full Emscripten web rebuilds; and a live browser re-test of at least one real specialization-constant-heavy feature (SDFGI again is the natural candidate) confirming correct rendering, not just successful pipeline creation.
